# Ventrix: финальная приёмка SaaS перед запуском

Дата: 2026-09-04. Проверяемая локальная версия: `c50bd42`.
Статус: план и предварительная проверка кода; НЕ акт готовности production.

### Исполнение: этап 1, первый блок

- Исправлено локально: сотрудник видит только собственную запись команды в API и боте.
- Авторизация сотрудника проверяет существование активного Employee того же tenant и совпадение Telegram user ID; незавершённая/чужая привязка не авторизуется.
- Устаревшие административные permissions сотрудника отсекаются при авторизации. Явный доступ к общим отчётам сохранён как отдельное разрешение.
- Отложенная доставка повторно проверяет tenant, сотрудника/membership, ответственного ситуации/сигнала/обязательства и состояние/адрес группы; при отзыве отменяется.
- Отменённые и delivery_uncertain уведомления не отправляются повторно. Отмена адресата отчёта учитывается как partial/cancelled, а не вечное pending.
- Добавлены регрессии чтения/переписки/ответа в чужой ситуации, отзыва membership, отключения уведомлений, переназначения, групп и некорректной идентичности.
- Проверено: полный pytest 224 теста; отдельный повтор тестов доставки после доработки агрегации статуса отчёта. Ruff пройден.
- Не выполнены пока: живая ролевaя приёмка Telegram/production, все маршруты export/PDF/кешей и аудит username-claim. Этап 1 целиком не объявлен завершённым.

## 1. Что уже подтверждено и чего подтверждение ещё нет

### Исполнение: этап 1, второй блок

- Локально исправлено: личный архив и report deep link не показывают отчёт без строки текущего сотрудника; API возвращает 404. Поддержан старый ключ rows наряду с employees.
- Проверен прямой вызов PDF callback от employee/observer: отказ до генерации/отправки документа. Общий PDF остаётся административной возможностью.
- Бот учитывает отдельное разрешение reports.read при выборе общего/личного списка и переходе по ссылке.
- Подключение рабочего аккаунта владельца не меняет его роль/permissions на employee.
- Username claim условно обновляет только непривязанную запись; повторная попытка не перепривязывает Telegram ID и не восстанавливает неактивное членство.
- Mini App сбрасывает сессию перед re-auth, скрывает защищённый экран и игнорирует старый ответ параллельного запроса. HTTP API и клиентские запросы помечены no-store.
- Проверено: полный pytest 229 тестов, Ruff, ESLint изменённых frontend-файлов, production build. Последнее согласование reports.read бота проверяется отдельным повтором bot/API suites.
- Визуальная проверка на реальных Telegram-устройствах и production-приёмка всё ещё не выполнены.
- Остаточный риск username-only приглашения: до первой привязки username не является постоянной идентичностью. Для окончательного закрытия нужен подтверждённый user ID либо подтверждение приглашения администратором; текущая правка не объявляет этот риск устранённым.
- Для проверки deployment-периметра: /metrics и /health/details в приложении не имеют проверки роли; проверить ограничения reverse proxy перед публикацией. Доступность извне пока не установлена.

### Исполнение: единое подключение рабочих аккаунтов

- Привязка подтверждённого Telegram ID к Employee и TenantMembership перенесена из API в общий TelegramConnectionService. Сессия, сотрудник и доступ сохраняются одной транзакцией для входа через бот и Mini App.
- Подключение к выбранному сотруднику проверяет tenant и Telegram ID; конфликт с уже существующим сотрудником отклоняется без переназначения рабочего аккаунта. Отказ отображается по-русски; отклонённая новая сессия отзывается, уже используемая сессия не затрагивается.
- Повторное подключение возвращает существующий ID аккаунта. Бот использует этот ID для каталога и первичного анализа вместо удалённого ID временной попытки входа.
- Повторный вход не меняет заданное администратором имя, пороги, уведомления и не восстанавливает отозванное членство. Роль владельца сохраняется.
- Незавершённый 2FA не создаёт сотрудника и не выдаёт доступ. Запоздалый ответ Telegram не возобновляет отменённый, заменённый или переназначенный запрос входа; проверяются идентификаторы challenge.
- Добавлены тесты обоих обработчиков бота (код/2FA), повторного входа, ошибочного Telegram ID, отмены во время RPC и параллельного подключения одного Telegram ID в двух разных проектах. Проверена адресация критической карточки руководителю и ответственному сотруднику.
- Финальный полный pytest: 250 тестов прошли, включая две проверки истёкшего входа. Ruff и git diff --check пройдены.
- Всё проверено локально с тестовой БД и имитацией Telegram. На сервере старые непривязанные сессии не исправлялись; их аудит/восстановление остаётся production-задачей. Автоматический /start сотрудника и подтверждение приглашений только по username — следующие отдельные работы.

## 2. Правила приёмки

Каждая проверка имеет: сценарий → ожидаемый результат → факт → доказательство → приоритет → повторный тест после исправления.
Статусы: подтверждено / дефект / не реализовано / не проверено / зависит от production-доступа.
P0: утечка, потеря данных, ошибочная отправка от чужого аккаунта. P1: блокировка основного сценария, недоставка, некорректная авторизация, потеря задач. P2: некритичная UX-проблема. P3: косметика.
Не обещать отсутствие всех возможных ошибок. Допуск к пилоту — только по проверенной матрице и измеренным ограничениям.
Продакшен-проверки сначала read-only. Отправки и аварийные сценарии — только в специально выделенных TEST-проектах, аккаунтах и группах, без сообщений реальным клиентам.

## 3. Матрица ролей и тестовые данные — P0

Подготовить два изолированных проекта A/B, двух владельцев команд, минимум двух сотрудников A и одного B, сотрудника без привязки, отозванное членство, наблюдателя; публичную и приватную тестовые группы.

| Роль | Ситуации | Отчёты | Аккаунты и группа | Системные логи |
|---|---|---|---|---|
| Владелец SaaS | Администрирование проектов; не неявный обход клиентской авторизации | Операционные показатели SaaS | Создание/запуск/состояние проектов | Только ему |
| Владелец/руководитель команды | Своего проекта | Своего проекта | Управление своим проектом | Нет |
| Сотрудник | Только назначенные ему | Только свои по умолчанию | Только состояние своего аккаунта, без админских настроек | Нет |
| Наблюдатель | По отдельной явно заданной политике, не через обход ссылкой | По разрешениям | Без управления | Нет |

Последнее требование пользователя заменяет прежнее правило видимости команды: сотруднику не показывать других сотрудников и их показатели. Переключатель доступа ко всем отчётам отдельно проверить; расширение доступа возможно только явно администратором и не открывает чужие ситуации автоматически.

Проверять не только скрытые кнопки: все GET/POST/PATCH API, callback_data, /start payload, report PDF, pagination, conversation, reply, экспорт, кеши и прямые ссылки. Чужая/удалённая карточка не раскрывает название, цитаты или существование записи. Членство и актуальные права повторно проверяются перед действием и доставкой.
Критерий: ни одной утечки между ролями/проектами, включая отозванные права и подменённый ID.

Путь: создание клиента → проверка токена BotFather → уникальная привязка бота → URL Mini App → установка меню Ventrix AI → контроль прав владельца команды → проверка готовности → активация.

- Проверить создание вручную/через AI-черновик, возвраты, отмену, повтор, прерывание FSM и продолжение.
- Неверный/отозванный токен, существующий бот другого проекта, временный сбой Telegram: понятное состояние, без ложного «готово».
- Проверить фактический getChatMenuButton после установки; повторная настройка не плодит сообщения.
- Развести «бот зарегистрирован», «polling работает», «Mini App настроен», «проект активен».
- Проверить перезапуск и ротацию токена без двух polling-процессов и без попадания токена в логи.
- Проверить ссылку приглашения владельцу команды и инструкции по первому входу.
Критерий: новый TEST-клиент проходит весь путь без ручных SQL-правок и получает нужный бот/меню/проект.

- Аудит всех точек завершения входа: Mini App onboarding, добавление сотрудника по номеру, бот, повторная авторизация.

## 6. Автоматический старт и мини-обучение сотрудника — P1

### Локальная реализация 2026-09-04

- Общий login-service ставит `telegram.start_employee_bot` в ту же транзакцию, что и привязку сотрудника. Runtime повторно проверяет наличие задачи при подключении; незапущенный бот не блокирует анализ, задача ждёт отдельно.
- Задача уникальна по проекту, боту и Telegram ID сотрудника. Используется официальный `messages.startBot` с сохранённым random_id: повтор после сетевой ошибки использует тот же ID, завершённая задача не отправляется заново.
- Перед RPC проверяются текущие tenant/сессия/сотрудник/membership, роль employee, Telegram ID реальной сессии и ID найденного бота. После сетевого разрешения username права проверяются ещё раз. Данные очереди сами по себе не дают доступа.
- FloodWait переносит задачу; блокировка бота не снимается автоматически. Результаты `requires_manual_start`/причина сохраняются в результате фоновой задачи, а не объявляются успешным открытием бота. Отображение этих диагностик в админском интерфейсе относится к этапу мониторинга.
- `bot_started_at` больше не выставляется при открытии Mini App; подтверждением служит полученный `/start`. Повтор автоматического старта не дублирует приветствие. При ошибке отправки первого приветствия маркер откатывается для повторного входа.
- Приветствие объясняет подключение руководителем и личные уведомления. Три шага имеют «Назад», пропуск, кнопку «Открыть Ventrix AI» и повтор из меню; общие отчёты описаны как отдельное разрешение руководителя.
- Первый deep link в свою ситуацию/отчёт не теряет целевую карточку, рядом доступно обучение. Исправлен реальный дефект deep link: обращение к отсутствующему `OperationalProblem.title` заменено отрывком сообщения клиента (`evidence`). Чужая ситуация не раскрывается.
- Новые тесты: фактическая постановка задачи при login, дедупликация, повтор RPC с тем же random_id, неверные ID, отзыв доступа до и во время RPC, блокировка/FloodWait/readiness, первое приветствие, повтор после ошибки и открытие своей/чужой карточки.
- Проверки: полный pytest — 268 passed; после добавления прямой кнопки Mini App повтор employee activation/navigation — 42 passed. Ruff и git diff --check без ошибок. Изменения локальные, без коммита/пуша/деплоя этого этапа.
- Ограничения: реальные Telegram-аккаунты не использовались, запуск на сервере не проверен. Нужен canary от сотрудника, проверка входящего `/start`, кнопки Ventrix AI и доставки первой личной карточки. Учёт старых ошибочных `bot_started_at` на production требует отдельного read-only аудита перед коррекцией.
- Справка Telegram: https://core.telegram.org/method/messages.startBot (метод пользовательской сессии; random_id для защиты от повторной отправки).

Предлагаемый путь: авторизация сессии → подтверждённая связь с сотрудником → durable-задача активации → поиск точного клиентского бота → проверка Telegram ID бота → однократный /start → приветствие → 3 коротких шага → личное меню.

- При подключении явно сообщать, что эта сессия запустит бота проекта и получит приветствие. Учесть, что авторизацию рабочего аккаунта выполняет его уполномоченный пользователь.
- Не искать бота по отображаемому имени. Проверять ID и username из BotInstance данного проекта.
- Отправка только через владельца account-scoped runtime/lease, не через дополнительный TelegramClient.
- Idempotency по tenant + bot + employee/user ID; восстановление после неоднозначного сетевого результата не должно спамить /start.
- Состояния: ожидает / запускается / подтверждён / требуется действие. Ошибка старта не должна обнулять успешное подключение сессии.
- Если бот заблокирован или отправка невозможна — безопасная ручная ссылка, без обхода блокировки и бесконечных повторов.
- Факт запуска подтверждается входящим update бота, не только постановкой outbound-задачи.
- Приветствие: кто добавил, какой проект/аккаунт отслеживается, какие уведомления будут приходить, куда обратиться при ошибочной привязке.
- Обучение: «Что отслеживается» → «Как открыть и обработать ситуацию» → «Мои отчёты и уведомления»; пропустить, назад, повторить. Первый переход из карточки не теряет целевую ситуацию.
- Проверить несовпадение владельца рабочей сессии и Telegram-аккаунта, с которого сотрудник открывает Mini App. Не расширять права автоматически.
Критерий: одно приветствие, правильный проект, сотрудник понимает свои действия и не видит административных кнопок.

## 7. Бот команды и Mini App — P1/P2

Пройти ролевую матрицу главных меню, карточек и обратных переходов на iOS, Android и Desktop Telegram; светлая/тёмная тема, узкий экран, клавиатура и длинные тексты.

- Все видимые кнопки имеют работающий маршрут и соответствуют доступным правам.
- Только одна переписка в ситуации, без повторного контекста и лишних разделов; сообщение клиента и объяснение различимы.
- Ответ появляется оптимистически, но «доставлено» не выставляется до подтверждения; при сбое понятное уведомление, возможность повторить без дубля, набранный текст не теряется.
- Настройки сессии свёрнуты; ползунки мгновенно отражают выбор, debounce/порядок запросов не теряют итоговое значение, ошибки сохранения видимы.
- Loading/empty/error/forbidden — разные состояния. При ошибке запроса не показывать «всё под контролем» или нулевую статистику как факт.
- Все названия/ошибки на русском; корректный HTML Telegram, экранирование цитат, переносы, лимит длины сообщения, валидная разбивка длинных отчётов.
- A11y: подписи/фокус/aria-expanded/размер касания; производительность: лишние запросы, race conditions, повторная авторизация, кеш после смены роли.
- Impeccable: одна пакетная визуальная проверка, исправления и одна подтверждающая проверка; без бесконечной косметической переработки.
Критерий: все основные действия проходят с нуля без ручного обновления/перезапуска бота.

## 8. Рабочие группы и доставка — P0/P1

### Исполнение: защищённое подключение и доставка

- Подключение группы теперь подтверждает только активный владелец/руководитель проекта, который одновременно является администратором Telegram-группы. Простое добавление или повышение бота, команда сотрудника/наблюдателя и событие `my_chat_member` лишь обнаруживают группу и не разрешают отправку.
- В `GroupIntegration` добавлено отдельное доказательство согласования (`approved_at`, `approved_by_telegram_user_id`) и привязка к конкретному клиентскому боту. Понижение прав, удаление бота, смена бота, Telegram 403 или миграция chat ID отзывают согласование; отключённую вручную группу фоновая проверка не включает обратно.
- Миграция `20260904_0023` переводит все ранее активные группы в `pending`: после выкладки руководитель должен один раз повторить `/ventrix_connect`. Это намеренный fail-closed переход, потому что старые строки не содержат доказательства того, кто разрешил доставку.
- Старые задачи в очереди повторно проверяют tenant, состояние группы, chat ID, согласование и доступность привязанного бота непосредственно перед отправкой. Групповые сообщения перестроены в короткие privacy-safe уведомления без цитат, личных показателей и callback-действий; кнопка ведёт в личный чат проектного бота, где права проверяются заново.
- Отчёт в группе сообщает только о готовности сводки. Предварительный сигнал, не подтверждённый глубокой проверкой, отправляет отмену, а не новую тревогу. Telegram `429` откладывает задачу на `retry_after`; окончательный `403` прекращает повторную доставку.
- Команды и callback-меню проекта в группе заблокированы: административные и персональные экраны доступны только в личном чате. API списка/настроек групп требует `groups.manage`, а неподтверждённую группу нельзя включить прямым PATCH.
- Инструкция в боте и Mini App теперь явно описывает обязательные права, отправку команды руководителем со своего неанонимного аккаунта, приватные группы и повторное подтверждение после удаления/добавления бота.
- Проверено локально: 284 теста полного backend-набора; отдельные регрессии на владельца, сотрудника, наблюдателя, постороннего администратора, удаление/возврат бота, ручное отключение, старую очередь, выбор привязанного бота, 403/429, отмену ложной тревоги и upgrade/downgrade/re-upgrade миграции. Ruff, `git diff --check`, ESLint изменённого экрана и production-сборка Next.js прошли.
- Не проверено без тестовой Telegram-группы и production runtime: фактическая доставка Bot API, поведение анонимного администратора на живом update, миграция реальной supergroup и новый deep link в Telegram iOS/Android/Desktop. Production-БД этим этапом не изменялась.

- Добавление/удаление бота, /ventrix_connect, проверка полномочий подключающего, обычная группа/supergroup, миграция chat ID, права отправки и приватные приглашения.
- Бот не считается подключённым лишь по приватной invite-ссылке: нужен подтверждённый chat ID и присутствие бота. Инструкция должна описывать реальный поддержанный путь и минимальные права.
- Проверить, что сотрудник без права управления не может незаметно привязать произвольную группу к проекту.
- Группа получает компактную privacy-safe карточку. Цитаты и персональные отчёты не должны раскрываться всем участникам только потому, что проблема доступна в Mini App её ответственному.
- Групповая кнопка → приватный бот → авторизация → нужная карточка; владелец видит свой проект, ответственный — свою ситуацию, чужой сотрудник — нейтральный отказ. Разные права определяются сервером, а не разными URL.
- Переключатели уведомлений, отчётов, quiet hours/thresholds, блокировка бота, 403/429, удалённая группа, повторы, cooldown и dedup.
- Проверять права повторно в момент отправки уже стоящей в очереди карточки.
Критерий: сообщение доставлено ровно нужному адресату; выключенная доставка не продолжается из старой очереди; ссылка не обходит доступ.

## 9. AI и параллельность нескольких проектов — P1

### Исполнение: общая квота, tenant fairness и изоляция провайдера

- Построена карта фактических AI-вызовов. Массовые пути: `signal.ai_triage`, `ai_batch_analysis`, `feedback.synthesize`, AI-проверка закрытия ситуации и narrative отчёта. Приветствие первого запуска и черновик клиента остаются интерактивными вызовами API/бота с безопасным fallback, а не задачами массовой очереди.
- Исправлен общий потолок AI: прежде `max_active_ai_requests` ограничивал только категорию `ai` и не суммировал `ai_fast`, `ai_heavy`, AI-narrative отчёта и AI-проверки reconciliation. Очередь теперь поддерживает ресурсный лимит по `cost_class`; worker применяет один DB-backed лимит ко всем этим AI-путям, поэтому запуск дополнительного процесса не создаёт отдельную квоту.
- AI-capable задачи маркируются `ai_fast`/`ai_heavy`. Не-AI стадии подготовки/агрегации сохранили отдельные heavy/report lanes, чтобы тяжёлая подготовка не занимала слот провайдера и уведомления не блокировались анализом.
- Исправлен starvation при backlog больше 100 задач одного проекта: кандидаты выбираются сначала по одному на tenant/category/resource lane, затем по приоритету и времени последнего обслуживания tenant. Большой проект больше не скрывает второй проект за окном первых 100 строк.
- Во все проектные вызовы DeepSeek передаётся нормализованный `user_id` tenant. Это дополняет локальную tenant-проверку поддерживаемой провайдером изоляцией планирования/кеша; общий лимит аккаунта при этом остаётся общим для всех ключей.
- Ошибка DeepSeek санитизирована: наружу и в логи не попадают ключ, URL или тело ответа. HTTP 429 сохраняет ограниченный `Retry-After` (по умолчанию 30 секунд), который очередь использует для следующей попытки; 429 и 5xx имеют конечные повторы, а постоянные 4xx (неверный ключ, баланс или параметры) завершаются после первой попытки.
- Исправлена метрика AI error rate: успешные записи со статусом `completed` раньше ошибочно считались сбоями, потому что сборщик признавал только `success`. Теперь оба допустимых успешных статуса не увеличивают счётчик ошибок; код `deepseek_http_429` доступен для последующего owner-monitoring.
- Регрессии: backlog 125 задач одного tenant не блокирует второго; разные экземпляры очереди разделяют категорийный и суммарный AI-лимит; синтетический пик 10 tenant × 3 задачи завершается без дублей/голодания и с максимум двумя одновременными AI-работами; `user_id`, 429/Retry-After и корректный error rate проверяются отдельно.
- Интерактивные AI-вызовы приветствия и owner-черновика теперь используют `SharedAIProvider`: перед запросом создаётся короткий `ai.interactive` lease в той же таблице `BackgroundJob`, поэтому API, owner-bot и все worker-процессы делят единый потолок. Lease поддерживается heartbeat, освобождается при успехе/ошибке, а после аварии помечается завершённым с ошибкой и не попадает в неподдерживаемый повтор очереди.
- Все write-транзакции SQLite теперь начинают критическую секцию через `BEGIN IMMEDIATE`: проверка доступной квоты и запись lease атомарны не только между корутинами, но и между отдельными ОС-процессами. Отдельный multiprocessing-тест подтверждает, что второй процесс не проходит к операции до освобождения первого.
- Полный локальный backend-набор после изменений: 297 тестов; Ruff и `git diff --check` прошли.
- Пока не доказано production-замерами: реальная пропускная способность DeepSeek, SQLite contention между отдельными ОС-процессами, предел CPU/RAM и время уменьшения backlog после пика. Резервный worker не включён автоматически до baseline; его безопасно запускать только с тем же DB и теми же лимитами.

- Карта всех AI-вызовов: fast triage, deep batches, проверки устранения, narrative отчётов, AI-черновики администратора. Выявить вызовы вне общего лимитера.
- Проверить бюджеты контекста/токенов, границы диалогов и tenant, schema validation, неверный JSON/ID, повтор пакета и устаревший результат после ответа сотрудника.
- Общий для процессов лимит по провайдеру/ключу плюс лимиты tenant и категорий. Одновременные запросы не должны менять общий клиентский контекст или смешивать ответы.
- Timeout, 429, 5xx, плохой ключ, исчерпание баланса: bounded retries, backoff/jitter, Retry-After при наличии, circuit breaker и сообщение владельцу SaaS. Не повторять бесконечно ошибки конфигурации.
- Нагрузочная матрица: 2 → 5 → 10 синтетических проектов, пики новых сообщений, одновременные первичные загрузки и отчёты, медленный AI, перезапуск worker.
- Проверить fairness, отсутствие starvation, независимость уведомлений/API от тяжёлого анализа, release/reclaim lease, отсутствие дублей после crash.
- Резервный worker — сначала один ограниченный consumer с уникальным worker_id под общей координацией, а не безлимитное масштабирование. Включать после замеров и контролировать cooldown/hysteresis. Дополнительный worker не добавляет квоту общему API-ключу.
- SQLite: writer contention, busy retries, диск/WAL/checkpoint, CPU/RAM и queue age. Если лимит базы достигнут — зафиксировать предел пилота и план PostgreSQL/очереди, не лечить добавлением процессов.
Критерий: ни потери/дублирования задач, ни смешивания данных; backlog после пика уменьшается; все проекты получают обслуживание. Численные SLO утвердить по baseline сервера, не выдавать выдуманный запас мощности.

## 10. Качество ситуаций и отчётов — P1

### Исполнение: точность ситуаций и доказательные отчёты

- Регрессионный корпус подтверждает пользовательские примеры: вопрос «Звучит интересно, а что за сервис?» и вопрос о цене после ответа сотрудника не остаются рабочими проблемами; отказ/благодарность, несколько сообщений, историческая загрузка, содержательное редактирование и голосовое без расшифровки обрабатываются без выдуманного действия.
- Медиа без текста теперь сохраняется в AI-контексте только как метаданные вложения. Голос, фото или видео сами по себе не считаются вопросом, жалобой, документом, интересом или обещанием; документный сигнал требует текста либо настоящего document MIME/расширения.
- Положительные исходы отделены от рисков: подтверждённый интерес, согласованный follow-up, созвон и продажа считаются только по явному доказательству и существующим message ID. Презентация сотрудника или обсуждение цены не являются продажей/интересом клиента.
- Исправлен расчёт времени ответа: ожидание хранится отдельно для каждого диалога, поэтому входящее сообщение из одного чата больше не связывается с ответом из другого. Для сотрудника сохраняются исходящие сообщения, охваченные диалоги, ответившие с явным знаменателем и процентом, среднее время/динамика, интерес, follow-up, созвоны и продажи.
- В отчёт сотрудника и руководителя добавлены текущие незакрытые ситуации с username/названием диалога, возрастом ожидания и коротким исходным доказательством. Сотрудник получает только строки и ситуации своего Employee; групповая версия остаётся без цитат и персональных показателей.
- Устранено ограничение доставки первыми восемью сотрудниками: ограничение применяется только к длине общей Telegram-сводки, персональная сводка ставится в очередь каждому активному сотруднику с действующим membership и включёнными уведомлениями. Проверено сценарием на девяти сотрудниках.
- Недельное расписание формирует семидневное окно. Границы отчёта фиксируются `period_end` планового запуска и предыдущим завершённым периодом, поэтому задержанный запуск не захватывает будущие сообщения. Старые активные ситуации переносятся как carry-over; удалённые сообщения не попадают в счётчики.
- AI narrative валидируется строгой Pydantic-схемой: строка вместо списка, лишние поля и некорректные элементы приводят к безопасной фактической сводке, а не к поломанному клиентскому тексту. PDF и Mini App показывают новые показатели по-русски и без выдуманных значений.
- Проверено локально: полный backend-набор — 302 теста; Ruff, ESLint изменённого отчётного экрана, production-сборка Next.js, `git diff --check` и генерация валидного PDF прошли.
- Не проверено без production/живого Telegram: фактическая доставка по расписанию в часовом поясе клиента, отображение длинной сводки на реальных iOS/Android WebView и стабильность DeepSeek narrative на реальном потоке. Эти пункты переходят в этапы 12–13 и не считаются подтверждёнными этим локальным прогоном.

- Регрессионный корпус реальных обезличенных ошибок: «А после цена какая?» + ответ, интерес без пропуска, спасибо/отказ, несколько входящих, голосовое/медиа, поздний edit/delete, исторические сообщения.
- Проверка после последнего ответа и перед отправкой карточки; интерес ≠ проблема, последнее входящее ≠ SLA breach. Положительные бизнес-результаты считать отдельно от рисков.
- Для каждого сотрудника: отправлено сообщений/охвачено диалогов, ответившие и явный знаменатель процента, текущие ожидания с возрастом, подтверждённый интерес/созвоны, динамика, рекомендации с доказательствами.
- Учитывать старые незакрытые ситуации за пределами отчётного периода. «За всё время» ограничить реально доступной историей; размер внешней базы контактов не выдумывать.
- Daily/week/month: правильные границы timezone, повтор запуска, quiet hours, период без активности, частичный анализ, опоздание, расписание после изменения настроек.
- Сотруднику доставляется только его версия; руководителю — команда; группе — разрешённая безопасная версия. Ссылки/PDF/AI narrative не обходят этот фильтр.
Критерий: каждое число воспроизводимо из сохранённых данных; выводы не противоречат последующим сообщениям; доставка и архив совпадают.

## 11. Мониторинг и логи в боте владельца SaaS — P1

### Исполнение: локальный контур наблюдаемости

- В административном боте экран «Состояние» показывает ревизию, SQLite, owner-bot, heartbeat API/scheduler/client-bots/worker, точную глубину и возраст очереди, AI ошибки и p95, ошибки доставки, просроченные отчёты, SQLite locks за последний час, диск и доступную host memory. Экран «Ошибки» раскрывает AI-коды и очередь по категориям.
- API, owner-bot, client-bots и worker регистрируют ограниченные heartbeat-записи; scheduler продолжает обновлять собственный heartbeat. Длинный идентификатор worker нормализуется до 64 символов с устойчивым hash suffix, поэтому рестарты не раздувают ключ произвольной строкой.
- Глубина активной очереди и самый старый backlog теперь считаются SQL-агрегатами по всему набору задач, а не по последним 2000 строкам. Ошибки AI/доставки/jobs/SQLite locks/FloodWait имеют явное часовое окно; latency и rate остаются ограниченными диагностическими выборками.
- Добавлены существенные owner-alerts: stale/stopped runtime, старый backlog, spike доставки, AI auth/quota/429, серия SQLite locks и низкий остаток диска. Состояние сохраняется, поэтому повторный tick не создаёт alert storm; смена состояния создаёт отдельное recovery-уведомление. Alert сначала надёжно ставится в очередь с idempotency key и только затем фиксируется как отправленный монитором.
- Кнопки владельца ограничены фиксированными действиями: обновить, ошибки, безопасные JSONL-события за 1 или 2 часа. Выгрузка строится в памяти, ограничена 5000 событиями/1,5 МБ и не принимает путь, shell-команду или произвольный период. В неё входят только allowlisted служебные поля; payload, заголовки и тексты диалогов не читаются.
- `/metrics` и `/health/details` закрыты owner API token. Выгрузка в Telegram дополнительно проверяет server-side ID platform owner до обращения к БД. Structured logger редактирует bot tokens, authorization/API keys, initData, OTP/2FA/password/code и телефоноподобные значения как в тексте события, так и в разрешённых context fields.
- Проверено локально: Ruff для `services`, `tests`, `scripts`; полный backend-набор — 313 тестов; отдельные регрессии точной очереди >2000 задач, часовых SQLite/FloodWait, секретов, owner-only логов, alert/recovery/dedup и Telegram Retry-After. Frontend: ESLint без ошибок (остались 152 предупреждения только в локальном Impeccable tooling) и успешная production-сборка Next.js.
- Не подтверждено этим этапом: фактические heartbeat и Telegram-доставка алерта после production deploy, host baseline за 24 часа, внешнее оповещение при полном падении сервера и фильтр выгрузки по отдельному проекту/процессу. Полное падение host нельзя надёжно обнаружить ботом на том же host; это обязательная production-задача этапа 12.

Экран «Система»: backend, scheduler, Telegram runtime, client-bots и worker pools с временем последнего heartbeat; версия релиза; backlog/возраст по категориям, ошибки доставки, AI latency/error rate, просроченные отчёты, SQLite contention, диск и память при доступных host-метриках.

- Кнопки «Обновить», «Ошибки», «Логи за 1 час», «Логи за 2 часа», фильтр проекта/процесса. Выгрузка асинхронной задачей, с ограничением размера и срока жизни файла.
- Только platform owner по server-side Telegram ID. Не выдавать этому обработчику произвольный shell, пути к файлам или Docker socket ради скачивания логов.
- JSONL/текст: timestamp UTC, component, level, tenant/job/correlation ID, stage, error code; без токенов, initData, OTP, 2FA, session strings, headers и тел переписок.
- Собирать логи всех процессов, а не только owner-bot stdout. Срок хранения и ротация ограничены; временные выгрузки удаляются по TTL.
- «Лайв» = немедленные существенные алерты + обновляемый status, а не бесконечный поток всех строк в Telegram. Дедуп, cooldown, recovery-уведомление, защита от alert storm.
- События: пропавший heartbeat, backlog растёт, delivery failure spike, AI auth/quota issue, disk low, частые locks. Не слать новый алерт на каждый retry.
- При полном падении host сам бот не сможет оповестить: отдельный внешний health-monitor должен контролировать недоступность.
Критерий: искусственная ошибка видна владельцу, восстановление видно, файл соответствует периоду и не содержит секретов; клиентские роли не могут скачать его.
